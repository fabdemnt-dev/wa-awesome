# 月秤の決闘 オンライン2人対戦 正式仕様書

## 1. 文書の位置付け

本書は、wa-awesome（GitHub Pages側）の「月秤の決闘」へ追加するオンライン2人対戦の正式仕様を定める。

実装時は本書をオンライン版の正本として扱う。ただし、既存の1人用CPU戦のゲームルール、月札効果、効果処理順、勝敗条件および確定済みUIを変更する根拠にはしない。

オンライン基盤の主要参考実装は、同じwa-awesome内の「影札の交渉」オンライン版とする。

「影札の交渉」オンライン版が使用する基盤は次のとおりである。

- Firebase Anonymous Authentication
- Cloud Firestore
- Firebase Realtime Database
- Firebase Callable Cloud Functions

Discord認証およびCloudflare D1は使用しない。これらは別のChatGPT Site側のオンラインゲーム基盤であり、本仕様へ混在させない。

## 2. 対象範囲

本書の対象は、月秤の決闘のオンライン2人対戦初版である。

既存の1人用CPU戦は維持する。将来の入口は次の2系統とする。

- 1人で遊ぶ：現在のCPU戦
- 2人で遊ぶ：オンライン2人対戦

初版ではCPU版とオンライン版を別ページ、別状態管理とする。オンライン対応を理由に既存CPU版を大規模にリファクタリングしない。

## 3. プレイヤー人数と席

オンライン版は次の構成とする。

- 人間2人
- 2席固定
- 純粋な1対1
- チームなし
- 初期NPCなし

影札の交渉にある4席、チーム制および「人間＋NPC 対 人間＋NPC」の構造は持ち込まない。

## 4. 部屋の作成と開始

部屋の基本フローは次のとおりとする。

1. 1人目が部屋を作成する。
2. 作成者が招待コードを相手へ共有する。
3. 2人目が招待コードで参加する。
4. 2人が待機室へ揃う。
5. ホストが「決闘を始める」を押す。
6. サーバーがゲームを開始する。

2人が揃った瞬間の自動開始は行わない。

内部roomIdはUUIDを基本とする。ユーザー向け招待コードは影札の交渉のHMAC保護方式を参考にし、招待コードのsecretを平文保存しない。

新しいUIDによる参加は待機中の部屋に限る。ゲーム開始後は新しいUIDの参加を拒否する。同じUIDによる進行中の自席への復帰は、新規参加とは区別する。

## 5. 認証、本人確認、席の保護

本人識別にはFirebase匿名UIDを使用する。

同一UIDが同じ部屋で複数席を取得できない構造とする。状態変更Callableでは操作に応じて、少なくとも次をサーバー側で検証する。

- 認証UID
- roomId
- gameId
- seat
- phase
- round
- stateVersion
- 対象操作を行える本人か

クライアントが指定する席情報だけを信用してはならない。認証UIDとサーバー側のmember・seat対応から操作席を確定する。

初版の復帰保証は、同じブラウザ等で同一Firebase匿名UIDを維持している場合に限る。匿名UIDを失った場合の本人回復および複数端末への席引継ぎは初版対象外とする。

## 6. オンラインゲーム状態の分離

保存状態は、少なくとも次の3領域へ明確に分離する。

### 6.1 server-only state

サーバーだけが読み書きできる領域とし、次を保持する。

- 双方の未公開札
- 双方の未公開模倣先
- 効果解決前の内部状態
- サーバー処理に必要な秘密情報

### 6.2 本人専用private state

認証UID本人だけが取得できる領域とし、次を保持または返却する。

- 自分の未使用札と使用済み札
- 自分の提出状態
- 自分に提示する合法な模倣候補
- 復帰時に本人へ必要な情報

### 6.3 公開済みpublic/result state

部屋の参加者双方へ返してよい情報だけを保持する。

- 現在のラウンドとphase
- 双方の表示名と月影
- 秘密を含まない待機状態
- 同時公開後の双方の実札
- 公開可能になった模倣結果
- 効果結果
- 履歴
- 最終結果または対戦中断

相手の未公開札および未公開模倣先を、public snapshot、読取可能なFirestore領域、HTMLまたはJavaScriptへ含めてはならない。UIで非表示にするだけの実装は禁止する。

## 7. 札の秘密提出と同時公開

各ラウンドの実札選択は次の順序で処理する。

1. プレイヤーが自分の未使用札から1枚を選ぶ。
2. 「この札で決定」を押す。
3. サーバーへ実札を秘密提出する。
4. 相手が未確定の場合は待機状態になる。
5. 双方の秘密提出が揃う。
6. サーバーが1つの公開状態を生成する。
7. 双方の実札を両クライアントへ同時公開する。

片方だけが先に公開される状態を作らない。相手が確定する前は、相手の札ID、札種、効果、画像を推測できる情報を返さない。

公開前に返してよいのは、秘密を含まない待機状態だけとする。

## 8. サーバーを唯一のゲーム正本とする

オンライン版では、Callable Cloud Functions側を唯一のゲーム正本とする。

サーバー側で管理・計算する対象は次のとおりである。

- 月影
- 使用済み札
- 6種類の月札効果
- 静止の月
- 返照の月
- 新月の誓い
- 偽りの月
- 模倣候補
- 模倣結果
- 無効化と不発
- ラウンド
- 履歴
- 途中決着
- 6ラウンド終了
- 勝利、敗北、引き分け
- 対戦中断

クライアントから月影、勝敗、効果結果、相手札、使用済み札全体などを直接指定させない。

既存CPU戦のカード名、効果、数値、効果処理順、勝敗条件をオンライン化のために変更しない。サーバー側ルールは、CPU戦の確定仕様と一致する純粋関数として実装し、テスト可能な構造とする。

## 9. 偽りの月

既存CPU戦と同じく、偽りの月は「実札公開後に模倣先を選択する」ルールを維持する。

処理順は次のとおりとする。

1. 双方が実札を秘密提出する。
2. 双方の実札を同時公開する。
3. サーバーが静止の月等による無効化を判定する。
4. サーバーが各プレイヤーの合法な模倣候補を計算する。
5. 有効な偽りの月を使用した本人だけへ合法候補を返す。
6. 本人が模倣先を秘密提出する。
7. 必要な模倣先がすべて揃った後、サーバーが公開可能な模倣結果を生成する。
8. サーバーがラウンドを最終解決する。

双方が偽りの月を出した場合は、双方がそれぞれ模倣先を秘密に選択する。一方の模倣先を、他方が自分の選択を確定する前に公開してはならない。双方の必要な選択が揃った後に公開・解決する。

静止の月等によって偽りの月が無効な場合、そのプレイヤーには模倣先選択を表示しない。合法な模倣候補がない場合は、既存ルールどおり不発としてサーバーが処理する。

模倣先選択中に再接続した場合は、サーバーの現在phaseと本人専用の合法候補を再取得する。模倣先や候補を端末へゲーム正本として保存しない。

## 10. ラウンド解決後と次ラウンド

ラウンド解決後は既存の「次のラウンドへ」を維持し、双方準備完了方式とする。

1. 一方が「次のラウンドへ」を押す。
2. サーバーへその席の準備完了を記録する。
3. 相手が未準備なら待機する。
4. 相手も押した時点で双方準備完了となる。
5. サーバーが次ラウンドを開始する。

一方が押しただけでは次ラウンドを開始しない。次ラウンド開始までは、既存仕様どおり前ラウンドの双方の公開札と結果を保持する。

一方が準備操作を完了し、もう一方が未準備の場合の準備待ち期限は120秒とする。期限を超過した場合、準備済みで待っている側に限り、次を表示する。

- もう少し待つ
- この決闘を終了する

「もう少し待つ」はサーバー上のdeadlineを60秒延長する。初版では延長回数に上限を設けない。「この決闘を終了する」は通常勝敗ではなく対戦中断として処理する。

準備待ち期限を超過しても、ランダム進行、自動準備または自動敗北にはしない。双方とも準備操作を行っていない場合、一方だけが相手を期限超過扱いとして単独中断することはできない。

## 11. ゲーム終了と再戦

通常のゲーム終了時は、既存の最終結果パネルを基本として使用する。

- 勝利
- 敗北
- 引き分け
- 最終月影
- 結果別WebP
- 「もう一度決闘する」
- 「🎪 おもちゃ箱へ戻る」

オンライン再戦は双方同意方式とする。

1. 一方が「もう一度決闘する」を押す。
2. サーバーへその席の再戦希望を記録する。
3. 相手が未希望なら待機する。
4. 相手も希望した時点で、同じ2人・同じ部屋の新しいゲームを開始する。

再戦待ち中でも「🎪 おもちゃ箱へ戻る」を利用できる。再戦専用の大きな別画面は作らない。

再戦希望を送信済みのプレイヤーが、明示的に「🎪 おもちゃ箱へ戻る」を選んだ場合は、再戦希望をサーバー側で取り消してからページを移動する。取消処理が成功する前にページを移動してはならない。取消処理が失敗した場合は現在画面に留まり、再試行できる状態にする。

一時的な通信切断、バックグラウンド移行、リロードまたは通信エラーだけでは再戦希望を自動取消しない。同じFirebase匿名UIDで復帰した場合は、サーバーsnapshotから本人の再戦希望を含む再戦待ち状態を復元する。

24時間の有効期間内では、初版の再戦回数に上限を設けない。再戦開始時は月影、札、使用済み札、公開札、模倣状態、ラウンド、履歴、結果、双方の準備・再戦希望を新しいゲーム用に完全初期化する。

## 12. 復帰

バックグラウンド移行、一時的な通信切断またはページ再読込だけで席を失わせない。

同じFirebase匿名UIDで戻った場合は、自分の進行中の席へ復帰できるようにする。入口には「進行中の決闘へ戻る」導線を用意する。

端末側へ保存してよい部屋復元情報は、初版ではroomIdだけとする。保存値には必要に応じて形式versionを付けてよいが、gameIdやゲーム内容は保存しない。現在のgameId、game、roundおよびphaseは、roomIdと認証UIDを検証したサーバーsnapshotから取得する。

札、模倣先、合法候補、月影、勝敗、効果結果、履歴などの秘密情報またはゲームstateをLocal Storageへ保存しない。Local StorageのroomIdは信頼せず、復帰時の実stateは認証UIDを検証したうえでサーバーから再取得する。

ページ起動時は、Firebase Authが既存の匿名認証状態を復元したことを確認してから新規匿名ログインを判断する。認証状態の復元を待たずに新しい匿名UIDを発行し、元の席を失わせてはならない。

## 13. presenceと切断

presenceにはFirebase Realtime Databaseを使用し、`onDisconnect`等でonline／offlineと更新時刻を記録する。

通常画面へONLINE、OFFLINE、接続ランプ等を常時表示しない。presenceだけを理由に即敗北、即中断またはNPC交代にはしない。

初版では切断者のNPC自動交代を実装しない。

一方が「🎪 おもちゃ箱へ戻る」でページを離れた場合も、即座に敗北または中断にはしない。一時的な切断と同様に扱い、同じUIDによる復帰を許可する。必要な操作の期限を超えた場合は、第15章から第18章のタイムアウト処理へ移行する。

## 14. オンライン専用UI

初版は現在の月秤の決闘の静かなUIを維持し、CPU版とほぼ同じ見た目を基本とする。

必要な待機状態だけ、次のような短い文章で示す。

- 対手の選択を待っています…
- 対手の模倣先選択を待っています…
- 対手が次のラウンドへ進むのを待っています…
- 対手の再戦希望を待っています…

オンライン情報を84px共通月夜背景の中へ追加しない。常時の通信情報や複雑なステータスパネルを追加しない。

オンライン版でも次の既存素材・UIを基本的に再利用し、オンライン化を理由に再デザインしない。

- 月札6枚のWebP
- 手札UI
- 中央公開札
- 高さ84pxの共通月夜背景WebP
- victory／defeat／draw結果画像WebP
- 結果パネル
- 履歴表示

## 15. 通常札選択のタイムアウト

通常札選択の初期期限は120秒とする。

時間切れでもランダム札を自動提出せず、自動敗北にも設定しない。

相手が期限を超過し、自分はそのphaseで必要な操作を完了している場合に限り、待っている側へ次を表示する。

- もう少し待つ
- この決闘を終了する

双方ともそのphaseで未操作の場合、後から戻った一方が相手を一方的に中断扱いにはできない。

## 16. 「もう少し待つ」

「もう少し待つ」はローカルUIを閉じるだけの操作ではなく、サーバー上のdeadlineを延長する状態変更操作とする。

初期延長値は60秒とし、初版では延長回数に上限を設けない。延長値は後から安全に調整できるサーバー側定数として扱う。

延長操作では、本人が必要な操作を完了済みであること、相手が期限超過中であること、対象game・round・phase・stateVersionが現在値と一致することをサーバーで検証する。

## 17. タイムアウト後の対戦中断

相手が期限を超過し、自分がそのphaseで必要な操作を完了している場合、待っている側は単独で「この決闘を終了する」を確定できる。

対戦中断は勝利、敗北、引き分けとは異なる専用stateとする。中断時にvictory、defeat、drawの結果画像を使用しない。

通常時に任意の「対戦をやめる」ボタンを常設しない。中断操作は、サーバーが中断可能条件を満たすと判定した場合だけ表示する。

## 18. 偽りの月の模倣先タイムアウト

模倣先選択の初期期限は60秒とする。

時間切れでも模倣先を自動選択せず、自動敗北にも設定しない。

相手の模倣先選択が期限を超過し、自分がそのphaseで必要な操作を完了している場合、通常札選択と同じく、待っている側は次を選択できる。

- サーバー上のdeadlineを60秒延長する
- 対戦を中断する

双方とも模倣先を未選択の場合、一方だけが相手を中断扱いにはできない。

## 19. 部屋のTTLとcleanup

部屋の有効期間は次の基準とする。

- 待機中：部屋作成から24時間
- 進行中：最後の有効なゲーム操作から24時間
- 正常終了後：終了時刻から24時間
- 対戦中断後：中断時刻から24時間

進行中の決闘を、部屋作成時刻から24時間が経過したことだけを理由に突然閉じてはならない。

進行中の期限を更新する有効なゲーム操作は、決闘開始、実札確定、模倣先確定、次ラウンド準備、再戦希望・取消、deadline延長および対戦中断とする。双方の入力が揃ったことによりサーバーが実行する公開、効果解決、次ラウンド開始および再戦開始も有効なゲーム処理として更新してよい。同じrequestIdの再送、拒否された操作、snapshot取得、presence更新などの読取・接続維持だけでは期限を更新しない。

正常終了時は終了時刻を、中断時は中断時刻をサーバー時刻で記録し、それぞれ24時間後をcleanup期限とする。

cleanupは、対象部屋のstatus、期限、現在gameを再確認してから行う。待機中、進行中、正常終了後、対戦中断後の各期限を混同せず、対応する基準時刻から24時間が経過したデータだけを対象とする。

## 20. requestIdによる冪等性

影札の交渉の方式を拡張し、次の状態変更操作にrequestIdを必須とする。

- 部屋作成
- 部屋参加
- 決闘開始
- 実札確定
- 模倣先確定
- 次ラウンド準備
- 再戦希望
- 再戦希望取消
- deadline延長
- 対戦中断

snapshot取得およびpresence更新にはrequestIdを要求しない。

サーバーはrequestIdを認証UID、操作種別、roomId、gameId、round等と対応付けて保存する。同じrequestId・同じ操作内容の再送は保存済み結果を返す冪等処理とし、同じrequestIdを異なる操作内容へ再利用した場合は拒否する。

## 21. stateVersionと古い操作の拒否

少なくとも次の操作ではstateVersionを検証する。

- 決闘開始
- 実札確定
- 模倣先確定
- 次ラウンド準備
- 再戦希望
- 再戦希望取消
- deadline延長
- 対戦中断

部屋作成、snapshot取得、presence更新にはstateVersionを要求しない。

部屋参加はFirestoreトランザクション内で、部屋status、定員、期限、既存member、席の空き等を再確認する。

各状態変更ではstateVersionだけでなく、gameId、round、phase、認証UID、seat、提出済み状態、対象札の合法性を必要に応じて検証する。古いroundまたは古いstateVersionの操作は、状態を変更せず拒否する。

同じphaseで双方が独立して行う入力は、同じ基準versionから正当に送信できなければならない。一方の実札提出、模倣先提出、次ラウンド準備または再戦希望を記録しただけで、他方の同じphaseに対する正当な入力を古いstateVersionとして拒否してはならない。

実装では、phase遷移時に更新するphase用versionと、席ごとの提出済み状態を分離するか、同等の安全な方法を用いる。双方の入力が揃って次phaseへ遷移した後は、遷移前versionによる追加操作を拒否する。

## 22. public snapshot allowlist

public snapshotはサーバー内部ドキュメントをそのまま返さず、月秤専用の明示的allowlistから構築する。

公開可能な項目は、phaseに応じて次から必要なものだけとする。

- room status
- gameIdおよびゲーム連番
- round
- phase
- stateVersion
- サーバー時刻と操作期限
- 双方の表示名
- 双方の月影
- 双方の未使用札枚数
- 秘密を含まない提出・待機状態
- 次ラウンド準備状態
- 再戦希望状態
- 公開後の双方の実札
- 公開可能になった模倣結果
- 効果結果
- 履歴
- 最終結果または対戦中断

次はpublic snapshotへ含めない。

- 相手の未公開札
- 相手の未公開模倣先
- server-only state
- 他人のprivate state
- 招待コードsecretとHMAC
- 内部レート制限情報
- requestId保存内容

本人専用情報は認証UIDに対応するprivate snapshotとして分離する。

### 22.1 Firestore直接アクセスとallowlist

初版の月秤オンラインクライアントは、ゲームstateをCallableのsnapshot経由で取得する。Firestore上の月秤ゲームデータは、クライアントから直接読み書きできないRulesを基本とする。これにより、Callableで構築したallowlistをFirestore直接読取で迂回できないようにする。

将来、公開領域をFirestoreから直接購読する設計へ変更する場合は、その公開ドキュメント自体をallowlist項目だけで構成し、server-onlyおよびprivate情報と物理的に分離したうえで、別途Rulesと漏洩試験を追加しなければならない。初版ではこの直接購読方式を採用しない。

### 22.2 論理phaseと遷移条件

実装上の名称は変更してよいが、サーバーは少なくとも次の論理状態を区別する。

1. 待機中：2人の参加とホスト開始を待つ。
2. 実札選択中：双方の秘密提出を受け付ける。
3. 実札公開済み：双方の実札を同じ公開結果として公開する。
4. 模倣先選択中：必要な本人だけから秘密の模倣先を受け付ける。
5. 解決中：サーバーだけが効果と月影を計算する。
6. ラウンド結果：公開札、模倣結果、効果結果、月影を保持する。
7. 次ラウンド準備待ち：双方の準備完了を受け付ける。
8. ゲーム終了：勝利、敗北または引き分けを保持する。
9. 再戦準備待ち：双方の再戦希望を受け付ける。
10. 対戦中断：通常勝敗と区別して中断結果を保持する。
11. 閉鎖済み：新しいゲーム操作を受け付けない。

実札公開後、模倣先選択が必要なプレイヤーがいなければ、模倣先選択中を経由せず解決へ進む。必要な模倣先が1件または2件ある場合は、すべて揃うまで解決へ進まない。効果解決後に途中決着または第6ラウンド終了条件を満たす場合はゲーム終了へ進み、それ以外はラウンド結果・次ラウンド準備待ちへ進む。

公開、解決、双方準備後の次ラウンド開始および双方同意後の再戦開始は、単一のサーバー正本に対してトランザクションまたは同等の排他制御で一度だけ確定する。

### 22.3 phase別の復帰snapshot

同じUIDで復帰したクライアントは、snapshotだけから次の表示と操作可否を再構築できなければならない。

- 待機中：自席、相手参加状況、ホスト開始可否
- 実札選択中・未提出：自分の未使用札、選択期限、提出可能状態
- 実札選択中・提出済み：自分が提出済みであること、相手待ち状態。相手の実札は含めない
- 実札公開済み：双方の公開実札と、模倣選択が必要かどうか
- 模倣先選択中・未提出：本人の合法候補と選択期限。相手の未公開模倣先は含めない
- 模倣先選択中・提出済み：本人が提出済みであることと相手待ち状態
- ラウンド結果・次ラウンド準備待ち：公開札、模倣結果、効果結果、月影、双方の準備状態
- ゲーム終了・再戦準備待ち：最終結果と双方の再戦希望状態
- 対戦中断：中断状態と利用可能な退出導線

クライアントは復帰時にローカルの途中選択をゲーム正本として復元せず、snapshotが示すサーバー確定状態を優先する。

## 23. セキュリティ要件

オンライン版はクライアントを信用しない前提で、次を必須とする。

1. 相手の未公開札をAPIレスポンスから取得できない。
2. HTMLまたはJavaScriptを解析しても、サーバー上の秘密情報を取得できない。
3. 他人のprivate stateをFirestoreから読めない。
4. クライアントからゲームstateを直接書けない。
5. 他人の席として操作できない。
6. 古いgame、round、phaseまたはstateVersionの操作を拒否する。
7. requestId再送で状態を二重処理しない。
8. 双方の実札確定前に片方だけを公開しない。
9. 模倣先は公開可能になるまでserver-onlyとする。
10. 月影、勝敗、効果結果はサーバーだけが計算する。
11. 再接続後は認証UIDに対応する本人の席だけを返す。
12. snapshotは明示的allowlistから構築する。
13. 招待コードsecretを平文保存しない。
14. Callableではすべての入力値を検証する。
15. Firestore Rulesでゲームデータへのクライアント直接書込みを拒否する。
16. RTDB Rulesで本人以外のpresence書換えを拒否する。
17. 別部屋への読取・状態変更を拒否する。

## 25. テスト要件

実装時は、純粋ルールテスト、Firebase Emulator統合テスト、必要なE2Eテストを用意する。実施していない確認を実施済みとして扱わない。

### 25.1 部屋・本人・席

- 2人の部屋作成、参加、待機室、ホスト開始
- 2人が揃っても自動開始しないこと
- 同一UIDの複数着席拒否
- ゲーム開始後の新規UID参加拒否
- 他人の席としての操作拒否
- 別部屋への越境読取・操作拒否

### 25.2 秘密情報と同時公開

- 相手の未公開札漏洩防止
- 双方の秘密提出
- 一方だけ提出した状態で札内容が公開されないこと
- 双方確定後の同時公開
- 同じ基準versionから送信された双方の正当な同時提出
- 他人のprivate state読取拒否
- server-only state読取拒否
- 月秤ゲームstateのFirestore直接読取拒否
- クライアント直接書込み拒否
- public snapshot allowlist

### 25.3 冪等性と古い操作

- 各対象操作のrequestId再送
- 同じrequestIdを異なる内容へ再利用した場合の拒否
- 異なるrequestIdによる二重提出拒否
- 古いstateVersion拒否
- 古いround・game・phaseの操作拒否
- 一方の入力記録だけで他方の同phase入力をstale扱いにしないこと
- 拒否操作の前後でゲームstateが変化しないこと

### 25.4 月札とゲームルール

- 満ちる月
- 欠ける月
- 返照の月1枚・2枚
- 静止の月
- 双方が静止の月
- 新月の誓いの公開時点判定
- 偽りの月の通常模倣
- 静止の月による偽りの月の無効化
- 模倣候補なしの不発
- 双方が偽りの月
- 模倣先の秘密保持と同時公開
- 双方の月影が0の引き分け
- 途中決着
- 6ラウンド完走
- 6ラウンド終了時の勝利、敗北、引き分け
- 効果処理順がCPU版の確定仕様と一致すること

### 25.5 タイムアウトと中断

- 通常札選択の120秒期限
- 模倣先選択の60秒期限
- ランダム自動提出を行わないこと
- 自動敗北にしないこと
- 60秒のdeadline延長
- 延長回数に上限がないこと
- 延長可能条件の検証
- 必要操作を完了した待機側だけが中断できること
- 双方未操作では一方的に中断できないこと
- 中断を勝敗・引き分けと区別すること
- 中断時に結果画像を使用しないこと

### 25.6 presenceと復帰

- 本人presenceのonline／offline
- 他人のpresence書換え拒否
- offlineだけでは敗北・中断・NPC交代にならないこと
- 一時切断後の再接続
- リロード後の進行中ゲーム復帰
- Firebase Authの復元前に別の匿名UIDを発行しないこと
- 同じUIDが本人の席だけへ戻ること
- Local Storageに秘密ゲームstateを保存しないこと
- 模倣先選択中の復帰
- 次ラウンド待機中の復帰
- 再戦待機中の復帰

### 25.7 次ラウンド・終了・再戦

- 次ラウンドの双方準備完了
- 一方だけの準備では進行しないこと
- 次ラウンド準備待ちの120秒期限
- 準備済みの待機側による60秒のdeadline延長
- 準備待ち期限超過時の対戦中断
- 双方未準備では一方的に中断できないこと
- 準備待ち期限超過でランダム進行、自動準備または自動敗北にならないこと
- 次ラウンド開始まで公開札を保持すること
- 再戦の双方同意
- 一方だけの希望では再戦を開始しないこと
- 再戦希望の取消
- 明示的なおもちゃ箱移動では再戦希望を取り消してから移動すること
- 一時切断、バックグラウンド移行、リロードおよび通信エラーでは再戦希望を維持すること
- 再戦希望取消失敗時は移動せず再試行できること
- 再戦時の完全初期化
- 再戦待ち中のおもちゃ箱導線
- 同じ部屋で複数回再戦できること

### 25.8 TTLとcleanup

- 待機中は作成から24時間で期限切れになること
- 進行中は最後の有効なゲーム操作から24時間であること
- 正常終了後は終了時刻から24時間保存すること
- 対戦中断後は中断時刻から24時間保存すること
- snapshot・presenceだけでは期限を延長しないこと
- 進行中ゲームが作成時刻だけで突然閉じないこと
- 終了・中断済み部屋のcleanup
- 招待locator・secret等の関連データcleanup

### 25.9 統合・表示・回帰

- 2ブラウザ相当のFirebase Emulator統合テスト
- 2人で第1ラウンドからゲーム終了まで進行できること
- 390px幅で秘密選択、待機、同時公開、模倣、結果、再戦を操作できること
- ページ全体に横スクロールが発生しないこと
- 月札画像、中央公開札、84px背景、結果画像が正常に表示されること
- CPU版のゲームルール・処理・表示に回帰影響がないこと

## 26. 実装時の変更範囲原則

オンライン版は専用ページ、専用クライアント状態管理、月秤専用Callable Functions、月秤専用Rulesおよびテストとして追加する。

既存CPU版をオンライン版へ置き換えない。共用する画像や確定UIは再利用してよいが、オンライン化を理由に既存CPU版のゲームルールやデザインを変更しない。

具体的なファイル構成とFirestoreコレクション名は、実装開始時に現在のリポジトリ構成を再確認し、影札との衝突を避けて決定する。ただし、本書で定めた秘密領域、本人専用領域、公開領域の分離を崩してはならない。

## 27. 実装開始前の確認事項

実装開始前には少なくとも次を確認する。

- 正規リモートmainとローカルHEAD
- 作業ツリーと未追跡ファイル
- 既存CPU版の最新ゲームルール
- 影札オンライン版の最新Firebase実装
- Firebaseプロジェクト設定
- 既存Functions、Rules、インデックス、workflowとの競合
- GitHub Pages側の入口と公開パス
- 本書と現在実装の間に矛盾がないこと

想定外の差分、競合、未確定の重要事項または安全に分離できない変更がある場合は、実装前に停止して報告する。
